DESIGN GUIDANCE FOR LARGE ANALYSIS/ARCHITECTURE TASKS

Use this file as design guidance when a task explicitly asks for a broad implementation in this area. It is intentionally detailed so contributors and coding agents can understand the preferred direction of the project.

How to interpret this document:
- This is guidance, not a universal hard spec for every task in the repo.
- If a user task or maintainer instruction conflicts with this file, follow the explicit task/instruction.
- For narrow bug fixes or scoped features, you may implement a smaller solution without satisfying every item here.
- For larger analysis, schema, or UI-overhaul work, this document describes the preferred architecture and acceptance goals.

You are a senior engineer improving an existing Python + PostgreSQL + GUI chess repertoire analyzer app.

CONTEXT (current behavior)
- Loads config/settings.ini; asks for missing paths and saves back.
- Repertoire: scans all PGNs under repertoire dir; each PGN game = separate repertoire “line”.
  - Line ID comes from PGN [Event] tag; should remain unique and non-empty for reliable analysis.
  - Matching is STRICT move order; transpositions are treated as different lines.
- Games: scans all PGNs under Chess.com games dir; keeps games where White or Black matches player name.
  - Parses moves and clock comments [%clk ...]; parses time control like 600+5; excludes daily/correspondence from time stats.
- Matching: picks repertoire line with longest exact-prefix move match.
  - Tracks max_matched_ply and first opponent/self deviation ply.
  - Compliance: FULLY_COMPLIANT, OPPONENT_DEVIATED, YOU_DEVIATED, BOTH_DEVIATED.
- Engine: Stockfish fixed depth (default 20) for first 30 plies; stores eval, best move, and centipawn loss on user moves only.
- Time: computes time spent from clock values and increment.
- Storage: everything stored in data/analysis.db (PostgreSQL). GUI reads from PostgreSQL only; analysis pipeline writes to PostgreSQL.

USER PREFERENCE
- Prefer keeping engine depth FIXED at 20. Performance improvements may be done via caching/incremental runs.

GOAL
If a task explicitly asks for this feature set, the preferred implementation approach is:
- Keep the analysis pipeline responsible for computing and writing to PostgreSQL.
- Keep the GUI read-oriented from PostgreSQL and avoid pushing heavy computation into the UI.
- Provide migrations so existing users’ DB can upgrade safely.
- Add incremental analysis so “Run Analysis” reprocesses changed files/games/lines and reuses cached engine results where practical.
- Add transposition-aware matching as an OPTIONAL mode controlled by config/INI, while preserving current strict behavior by default.

===========================================================
FEATURE SET TO IMPLEMENT
===========================================================

1) MATCHING MODES (Strict vs Transposition-aware)
Preferred config setting:
- matching_mode = STRICT | TRANSPOSITION

STRICT mode:
- preserve current matching (longest exact-prefix SAN move match).

TRANSPOSITION mode:
- match by POSITION (tabiya) rather than move order.
- Compute a normalized position key per ply (use FEN normalization; ideally add Zobrist hash).
- For each repertoire line, store position keys per ply.
- For each game, store position keys per ply.
- Preferred matching algorithm:
  - Find the repertoire line that gives the deepest match by position keys (prefix of positions).
  - Tie-breakers:
    1) deeper matched ply
    2) if equal, prefer line with closer move sequence similarity to game SAN prefix (or fewer mismatches earlier)
    3) if still tied, prefer line marked as primary (see “line priority” below), else deterministic (lowest line_id).
- Keep existing outputs: matched line_id, max_matched_ply, first self/opponent deviation ply, compliance label.
- Add new fields that describe match method and confidence.

2) BUILD A REPERTOIRE TREE (position -> allowed moves)
Currently each PGN game is a separate line. A preferred direction is to add a derived repertoire tree across all lines:
- For each position encountered in any repertoire line, store all legal repertoire moves that appear in any line from that position, with edges to next position.
- Mark each edge with:
  - source_line_id (one or more)
  - is_mainline (true if from a line marked “primary” or if it is the matched line continuation)
  - weight/frequency (count of how many lines contain the edge)

Use this tree to classify each game ply (especially deviations):
- IN_REPERTOIRE_MAIN: move matches the matched line continuation at that position.
- IN_REPERTOIRE_OTHER: move exists in repertoire tree from that position but not the matched line continuation.
- OUT_OF_REPERTOIRE: move not found in repertoire tree from that position.

This classification is most useful when it works in both STRICT and TRANSPOSITION modes.

3) IMPROVED COMPLIANCE + TAGGING
Preferred richer tags while keeping compatibility:
- who_left_first: YOU | OPPONENT | BOTH | NONE
- deviation_ply_you, deviation_ply_opponent (already tracked; ensure stored)
- recovered_to_repertoire: boolean (left tree then later re-entered a known position key)
- opponent_deviation_to_known: boolean (opponent deviated but landed in position that exists somewhere in repertoire tree)
- deviation_type (heuristic labels, not ML):
  - TRANSPOSITION (only when mode=STRICT but position matches a known repertoire position)
  - NOVELTY (first time a deviation move is seen at that position)
  - BLUNDER_LIKE (if your CPL at deviation ply exceeds threshold, e.g. > 150cp)
  - SIMPLIFICATION (large material reduction shortly after deviation)
  - ENDGAME_TRANSITION (material key crosses into endgame heuristic)

These tags are intended to power review prioritization.

4) GAME VIEW: “What did repertoire expect?” vs Engine best
Preferred per-game/per-ply detail additions at deviation ply:
- Your move (SAN + UCI)
- Repertoire mainline move (if known)
- Repertoire alternatives (top N moves from repertoire tree, with frequencies/source lines)
- Engine best move at depth 20
- Eval before/after (or eval at ply)
- Centipawn loss vs engine best (existing)
- Centipawn loss vs repertoire mainline move (new)
- Classification text such as:
  - “Repertoire move is still fine”
  - “Repertoire move is inaccurate here”
  - “You deviated into a worse line”
  - “Opponent deviation made line irrelevant”

Prefer not to change engine depth just to support these comparisons; reuse cached depth-20 evaluations when possible.

5) TIME USAGE: normalized stats + panic patterns
Preferred additions:
- normalize by time control (base+increment)
- per move: time_spent_fraction_of_start = time_spent / initial_base_seconds
- aggregate: %time in-book vs out-of-book (based on IN_REPERTOIRE_* classifications)
- detect patterns:
  - slow_in_book
  - instant_out_of_book
  - blunder_cluster_out_of_book

6) COVERAGE MAP + OPPONENT DEVIATION HEATMAP
Preferred aggregated features:
- For each “tabiya” (position key) that occurs in games:
  - frequency reached
  - opponent deviation moves frequency (top N SAN/UCI)
  - whether repertoire tree contains responses for those moves (covered/uncovered)
  - your score (W/D/L) when opponent chooses each deviation
- coverage metrics:
  - positions reached in your games that exist in repertoire tree / total positions reached
  - opponent deviations that are covered vs not covered
- Review prioritization suggestions:
  - positions where opponent deviates often and you have no repertoire response
  - positions where you deviate early and have high CPL or poor outcomes

7) INCREMENTAL ANALYSIS + CACHING
Preferred approach:
- Compute and store file hashes (or modified time + size) for repertoire PGNs and game PGNs.
- On Run Analysis:
  - Only reparse PGN files that changed since last run.
  - Only rerun engine analysis for positions/plies that changed or are not already cached.
- Cache engine results keyed by `(position_key, side_to_move, depth=20, multipv=1, engine_version optional)`.
- Reuse cached results across games/lines when the position repeats.

8) SCHEMA CHANGES (PostgreSQL) + MIGRATIONS
A preferred migration direction is to use a `schema_version` table and preserve existing data while moving forward.
Representative tables/concepts:
- positions(pos_id PK, fen_norm, zobrist, material_key, side_to_move)
- repertoire_lines(line_id PK, source_pgn, is_primary INT, metadata_json)
- line_positions(line_id, ply, pos_id, san_move, uci_move, next_pos_id, PRIMARY KEY(line_id, ply))
- repertoire_edges(pos_id, uci_move, next_pos_id, weight, sources_json, PRIMARY KEY(pos_id, uci_move, next_pos_id))
- games(game_id PK, source_pgn, white, black, result, time_control, date, your_color, your_rating, opp_rating, metadata_json)
- game_positions(game_id, ply, pos_id, san_move, uci_move, clk, time_spent, repertoire_class, PRIMARY KEY(game_id, ply))
- matches(game_id PK, matched_line_id, matching_mode, max_matched_ply, deviation_ply_you, deviation_ply_opp, compliance, who_left_first, recovered_to_rep, opponent_dev_to_known, tags_json)
- engine_cache(pos_id, depth, best_uci, eval_cp, wdl_json, analyzed_at, engine_id, PRIMARY KEY(pos_id, depth, engine_id))
- analysis_ply(game_id, ply, pos_id, eval_cp, best_uci, your_cpl, PRIMARY KEY(game_id, ply))

9) UI UPDATES (read-oriented)
Preferred additions:
- Games tab: matching_mode, repertoire_classification summary, who_left_first.
- Lines tab: coverage stats, opponent known/unknown deviation rates, average exit eval, in-rep-other-branch rate.
- Time usage tab: normalized time charts and panic pattern counters.
- Rating bands tab: in-book vs out-of-book performance/time.
- Review tab: missing coverage hotspots, early self-deviation with high CPL, poor performance positions weighted by frequency.

10) CONFIG UPDATES
Suggested defaults:
- matching_mode=STRICT
- enable_engine_cache=1
- incremental_analysis=1
- max_plies_engine=30
- review_top_n=25
- tabiya_top_n=10

IMPLEMENTATION NOTES
===========================================================
- Use python-chess for PGN parsing and FEN generation when applicable.
- SAN parsing should be robust; store both SAN and UCI moves where possible.
- FEN normalization should remove halfmove/fullmove counters while keeping castling rights, en passant, and side to move.
- Daily/correspondence games should remain excluded from time-based stats unless a task explicitly expands support.
- Prefer keeping engine depth fixed at 20 unless a task explicitly changes that constraint.
- Avoid breaking existing GUI behavior unnecessarily; add fields and views incrementally when practical.
- Useful tests for broad work in this area include:
  - transposition-aware matching correctness on known transposition examples
  - repertoire tree classification (main vs other vs out)
  - incremental analysis skipping unchanged files
  - engine cache reuse

DELIVERABLES FOR A FULL-SCOPE IMPLEMENTATION
1) Code changes implementing the requested feature set.
2) PostgreSQL migration script/module with schema_version handling.
3) Updated settings.ini template + code to upgrade existing INI.
4) UI updates wired to new DB fields.
5) Brief developer notes in README describing matching modes and new review metrics.

ACCEPTANCE GOALS FOR A FULL-SCOPE IMPLEMENTATION
- In STRICT mode, existing results should stay close to prior app results, aside from intentional fixes.
- In TRANSPOSITION mode, a transposed move order should match to the correct line deeper than STRICT would.
- Engine depth should remain 20 if that constraint still applies.
- Running analysis twice without changing PGNs should be faster and should not duplicate rows.
- Review surfaces should be able to highlight missing-coverage hotspots and early-deviation-with-high-CPL items from stored data.
